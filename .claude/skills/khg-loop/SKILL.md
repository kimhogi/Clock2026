# khg-loop — 공용 풀 라이프사이클 실행 루프 (multi-agent)

> 이 문서는 **특정 도메인에 묶이지 않은 범용 루프**다. MFC, 문서 작성, 리팩터링 등
> 어떤 스킬이든 이 루프를 뼈대로 삼아 자기 도메인의 "검증 방법"만 끼워 넣으면 된다.
>
> 두 개의 루프가 **중첩**되어 있다:
> - **바깥 루프 = 라이프사이클**: PRD→TRD→계획→구현→검증→테스트→회고. 멀티에이전트.
> - **안쪽 루프 = 마이크로 실행 루프**: FRAME→OBSERVE→PLAN→ACT→CHECK→REFLECT→DONE.
>   "구현" 단계에서 작은 변경 하나하나를 굴리는 데 쓰며, 작은 작업이면 이것만 단독으로 써도 된다.
>
> 다른 스킬에서 참조하는 방법:
> ```
> 이 작업은 khg-loop 스킬의 루프를 따른다.
> 검증(VERIFY)/테스트(TEST) 단계의 명령 = <도메인 검증 절차>를 사용한다.
> ```

---

## 0. 이 루프가 풀려는 문제

LLM 에이전트가 큰 작업에서 실패하는 전형적 패턴:

- 무엇을/왜 만드는지(**PRD**)와 어떻게 만들지(**TRD**)를 안 적고 바로 코딩 → 방향이 샌다.
- 한 번에 너무 많이 바꿔서 무엇이 깨졌는지 모른다.
- "다 됐다"고 선언하지만 **검증을 안 한다**.
- 단계 사이에 맥락이 흩어지고, 같은 실수를 반복한다(배움이 누적되지 않는다).

이 루프는 위를 구조로 막는다. 두 가지 핵심 원칙:

> **(1) 추측하지 말고 관찰하라. 한 번에 한 걸음. 매 걸음마다 검증. 검증되지 않은 것은 "완료"가 아니다.**
> **(2) 모든 단계의 산출물은 파일로 남긴다. 그것이 단계 간(그리고 에이전트 간) 유일한 인수인계 수단이다.**

이 설계는 GitHub의 PDCA 스킬(Plan-Do-Check-Act + 사람 검토 게이트 + TDD), Claude Code의
에이전트 루프(맥락 수집→행동→검증→반복), OODA 루프에서 검증된 것을 종합했다. (출처는 맨 아래.)

## 1. 산출물 작업공간 (artifacts workspace)

작업마다 전용 폴더를 만든다. **이것이 멀티에이전트 인수인계의 핵심이다** — 서브에이전트는
서로의 대화 맥락을 공유하지 못하므로, 디스크의 파일로만 주고받는다.

```
docs/loops/<task-id>/        # task-id = YYYYMMDD-<짧은-슬러그>
├── _state.md                # 현재 단계 / 게이트 상태 / 산출물 링크 / 결정 로그 (오케스트레이터가 관리)
├── PRD.md                   # 1. 제품 요구사항      (무엇을/왜)
├── TRD.md                   # 2. 기술 요구사항·설계  (어떻게)
├── plan.md                  # 3. 구현 계획(작은 태스크 체크리스트)
├── progress.md              # 4. 구현 진행 로그(안쪽 마이크로 루프 사이클 기록)
├── verification.md          # 5. 검증 결과(빌드/리뷰/TRD 대비 충족)
├── test-report.md           # 6. 테스트 결과(스위트 실행, Passed/Failed, 회귀)
└── retro.md                 # 7. 회고(잘된 점/문제/다음 사이클 액션, 루프 개선)
```

각 산출물의 양식은 **`${CLAUDE_SKILL_DIR}/templates/`** 의 동명 템플릿을 복사해 채운다.
다른 작업공간 경로를 쓰고 싶으면 `_state.md`에 명시하고 그 경로로 통일한다.

## 2. 멀티에이전트 오케스트레이션 (어떻게 돌리나)

**오케스트레이터**(이 루프를 시작한 메인 에이전트)는 직접 단계를 다 하지 않는다.
각 단계를 **전담 서브에이전트**에게 Agent 도구로 위임하고, 게이트를 지키며 조립한다.

### 단계 실행 레시피 (모든 단계 공통)
1. 직전 단계 산출물 경로를 확인한다 (`docs/loops/<id>/...`).
2. Agent 도구로 그 단계 담당 서브에이전트를 띄운다 (`subagent_type` 지정). 프롬프트에 반드시 포함:
   - **역할**(이 단계가 무엇인지) + **읽을 입력 산출물 경로** + **써야 할 출력 산출물 경로**
   - **사용할 템플릿 경로**(`${CLAUDE_SKILL_DIR}/templates/<단계>.md`)
   - **완료 기준(DoD)** 과 "끝나면 파일을 저장하고 3줄 요약만 반환하라"
3. 서브에이전트는 입력을 읽고 → 작업하고 → **출력 산출물 파일을 저장**하고 → 요약을 반환한다.
4. 오케스트레이터는 `_state.md`를 갱신하고 **게이트**(사람 승인 또는 자동 검증)를 통과시킨다.
5. 통과하면 다음 단계로. 막히면 해당 단계로 되돌아가 다시 위임한다.

### 단계 ↔ 담당 에이전트 매핑 (Claude Code 기준 권장값)
| 단계        | subagent_type        | 비고 |
| ----------- | -------------------- | ---- |
| PRD         | `general-purpose`    | 리서치가 필요하면 `Explore`로 사전 조사 |
| TRD(설계)   | `Plan`               | 아키텍트 역할 |
| 계획        | `Plan`               | 작은 태스크로 분해 |
| 구현        | `general-purpose`    | 내부에서 **안쪽 마이크로 루프**(6단계) 사용. 작은 변경은 오케스트레이터 직접 수행도 가능 |
| 검증        | `general-purpose`    | 코드 리뷰는 `/code-review` 스킬 병행 권장 |
| 테스트      | `general-purpose`    | 빌드/테스트 실행(도메인 명령) |
| 회고        | `general-purpose`    | 오케스트레이터가 직접 정리해도 됨 |

> 환경에 위 subagent_type이 없으면 가용한 범용 에이전트로 대체하고, 그래도 없으면
> 오케스트레이터가 단계를 순차 수행하되 **산출물 파일 저장 규칙은 그대로** 지킨다.

## 3. 바깥 루프 — 라이프사이클 단계 (순환)

```
            ┌─────────────────────────── 다음 증분(다음 사이클) ───────────────────────────┐
            ▼                                                                               │
  [1] PRD ─▶ [2] TRD ─▶ [3] PLAN ─▶ [4] IMPLEMENT ─▶ [5] VERIFY ─▶ [6] TEST ─▶ [7] RETRO ─┘
   무엇/왜    어떻게      태스크분해    (안쪽 루프)        빌드/리뷰     테스트green   회고/개선
   ⟂게이트    ⟂게이트     ⟂게이트       ⟂green           ⟂green       ⟂green
   (사람승인) (사람승인)   (사람승인)    (자동)           (자동)       (자동)
```

### [1] PRD — 제품 요구사항 (무엇을, 왜)
- 입력: 사용자 요청. 출력: `PRD.md`(템플릿 사용).
- 담는다: 배경/문제, 목표·비목표(scope/non-scope), 사용자 스토리, **검증 가능한 수용 기준**, 리스크, 오픈 질문.
- 게이트: **사람 승인.** 수용 기준이 모호하면 여기서 멈추고 1~3개 질문으로 좁힌다.

### [2] TRD — 기술 요구사항·설계 (어떻게)
- 입력: `PRD.md`. 출력: `TRD.md`.
- 담는다: 아키텍처/구성요소, 인터페이스·시그니처, **변경할 파일 목록**, 데이터/상태, **테스트 전략**, 대안·트레이드오프.
- 게이트: **사람 승인.**

### [3] PLAN — 구현 계획 (작은 태스크로 분해)
- 입력: `TRD.md`. 출력: `plan.md`.
- 담는다: 순서 있는 **작은 태스크 체크리스트**. 각 태스크는 *하나의 검증 가능한 변경* + 그에 대응하는 테스트.
- 게이트: **사람 승인.**

### [4] IMPLEMENT — 구현 (안쪽 마이크로 루프로)
- 입력: `plan.md`. 출력: 코드 변경 + `progress.md`.
- `plan.md`의 태스크를 **하나씩** 안쪽 마이크로 루프(아래 4장)로 처리한다. TDD: 실패 테스트 먼저 → 최소 구현 → green.
- 각 마이크로 사이클 결과를 `progress.md`에 한 줄씩 누적.
- 게이트: 모든 태스크가 안쪽 루프 기준 green.

### [5] VERIFY — 검증 (정확성/설계 충족)
- 입력: 변경 + `TRD.md`. 출력: `verification.md`.
- **도메인 검증 명령(빌드 등)** 을 실행하고, **코드 리뷰**(`/code-review` 권장)로 정확성·회귀·새 경고를 점검.
- TRD 대비 충족 여부와 PRD 수용 기준 대비를 체크.
- 게이트: 빌드 성공 + 치명 리뷰 이슈 없음(자동/반자동).

### [6] TEST — 테스트 (스위트 실행, 수용 확인)
- 입력: 변경 + `PRD.md`(수용 기준). 출력: `test-report.md`.
- **전체 테스트 스위트 실행**(도메인 명령), 부족하면 테스트 추가. Passed/Failed·회귀·커버 범위 기록.
- 게이트: **전체 green** + PRD 수용 기준 충족.

### [7] RETRO — 회고 (순환의 연결고리)
- 입력: 전 산출물. 출력: `retro.md`.
- 잘된 점/문제/배운 점/다음 사이클 액션, 그리고 **루프 자체 개선점**.
- 다음 증분이 있으면 그 인사이트를 안고 [1] PRD로 **순환**. 없으면 DONE.

> **경량 모드**: 작업이 작고 요구가 명확하면 PRD/TRD/PLAN을 한 문단으로 압축하거나 건너뛰고
> 곧장 IMPLEMENT의 안쪽 마이크로 루프로 가도 된다. 단, VERIFY/TEST 게이트는 절대 건너뛰지 않는다.

## 4. 안쪽 루프 — 마이크로 실행 루프 (구현 단계의 엔진, 단독 사용 가능)

```
[0] FRAME ─▶ [1] OBSERVE ─▶ [2] PLAN ─▶ [3] ACT ─▶ [4] CHECK ─▶ [5] REFLECT ─▶ (반복/DONE)
 목표 고정    맥락 수집       한 걸음      최소 변경    검증          반영
```

- **[0] FRAME**: 이 태스크의 검증 가능한 완료 기준을 한 문장으로.
- **[1] OBSERVE**: 고치기 전에 관련 코드/로그를 **실제로 읽는다**. 추측 금지. 넓으면 Grep/Glob/Explore로 fan-out.
- **[2] PLAN**: 지금 사이클에서 할 **단 하나의** 변경을 정한다(나머지는 다음 사이클).
- **[3] ACT**: 그 한 걸음만 실행. scope creep 금지. 주변 코드 스타일·관례를 따른다.
- **[4] CHECK**: **도메인 검증 명령을 실행하고 출력을 실제로 본다.** 통과/실패(원문)/건너뜀(이유)을 기록.
- **[5] REFLECT**: 성공이면 다음 걸음. 실패면 가설을 바꾼다 — **같은 변경을 그대로 재시도 금지**.
  같은 실패 2회면 OBSERVE로 더 깊이, 3회 막히면 멈추고 보고(무한 루프 금지).

## 5. 게이트 & 가드레일

- **사람 검토 게이트**(PRD/TRD/PLAN): 다음 단계로 넘어가기 전 승인을 받는다. 모호하면 질문으로 좁힌다.
- **자동 게이트**(VERIFY/TEST): 빌드 성공·테스트 green이 아니면 통과 아님.
- **무한 루프 금지**: 한 단계/한 마이크로 사이클 3회 연속 실패 → 멈추고 진단·막힌 지점 보고.
- **검증 없는 완료 금지**: VERIFY/TEST를 건너뛴 채 "완료" 선언 금지.
- **되돌리기 어려운 행동**: 삭제/덮어쓰기/외부 전송/푸시 전엔 확인. 내가 만들지 않은 것을 지우거나
  덮어쓰기 전엔 내용을 먼저 확인하고, 설명과 모순되면 진행 대신 알린다.
- **정직한 보고**: 실패는 출력과 함께, 건너뜀은 이유와 함께. `_state.md`에 항상 실제 상태를 반영.
- **인코딩 보존**: 비-UTF8/BOM 파일(예: CP949·UTF-16)은 도메인 하네스를 통해서만 편집한다.
  직접 편집은 한글 등 멀티바이트 텍스트를 손상시킬 수 있다. (MFC: khg-mfc 스킬의 scripts/mfc_encoding.py begin/end)

## 6. 다른 스킬에서 쓰는 법 (계약, contract)

이 루프를 가져다 쓰는 스킬은 아래 "구멍"만 채우면 된다.

| 구멍 (hook)            | 채워 넣을 것                                           |
| ---------------------- | ------------------------------------------------------ |
| `VERIFY/TEST 명령`     | 빌드·테스트·실행 등 **도메인 검증 명령** (가장 중요)    |
| `OBSERVE 대상`         | 어떤 파일/로그/도구로 관찰하는가                       |
| `테스트 작성 관례`     | 테스트 프레임워크·assert 관례                          |
| `작업공간 경로`        | 기본 `docs/loops/<id>/` 외 다른 경로를 쓸 경우         |

예시(khg-mfc 스킬): 그 스킬의 loop.md 가 VERIFY=MSBuild 빌드,
TEST=CppUnitTest(vstest) 실행으로 위 구멍을 채운다.
