# loop — 공용 실행 루프 (reusable agentic loop)

> 이 문서는 **특정 도메인에 묶이지 않은 범용 루프**다.
> MFC, 문서 작성, 리팩터링 등 어떤 스킬이든 이 루프를 뼈대로 삼아
> 자기 도메인의 "검증 방법"만 끼워 넣으면 된다.
>
> 다른 스킬에서 참조하는 방법:
> ```
> 이 작업은 @.claude/skills/loop/SKILL.md 의 루프를 따른다.
> CHECK 단계의 "검증" 자리에는 <도메인 검증 명령>을 사용한다.
> ```

---

## 0. 이 루프가 풀려는 문제

LLM 에이전트가 실패하는 전형적 패턴은 다음과 같다.

- 맥락을 덜 읽고 **추측으로** 코드를 고친다.
- 한 번에 **너무 많이** 바꿔서 무엇이 깨졌는지 모른다.
- "다 됐다"고 선언하지만 **검증을 안 한다**.
- 같은 실수를 **반복**한다(배움이 누적되지 않는다).

이 루프는 위 네 가지를 구조로 막는다. 핵심 원칙은 단 하나:

> **추측하지 말고 관찰하라. 한 번에 한 걸음. 매 걸음마다 검증. 검증되지 않은 것은 "완료"가 아니다.**

이 원칙은 Claude Code 자체의 에이전트 루프(맥락 수집 → 행동 → 검증 → 반복),
군사 의사결정 모델 OODA(Observe-Orient-Decide-Act), 제조/품질 관리의
PDCA(Plan-Do-Check-Act)에서 공통으로 검증된 것이다. (출처는 맨 아래 참고.)

## 1. 루프 한눈에 보기

```
        ┌──────────────────────────────────────────────────────┐
        │                                                        │
        ▼                                                        │
  [0] FRAME ──▶ [1] OBSERVE ──▶ [2] PLAN ──▶ [3] ACT ──▶ [4] CHECK
   목표 고정      맥락 수집        한 걸음       최소 변경     검증
        │                                                        │
        │                          ┌──────── 실패 ───────────────┤
        │                          ▼                             │
        └────── 목표 달성? ◀── [5] REFLECT ◀──── 성공 ───────────┘
                   │                반영/기록
                  YES
                   ▼
              [6] DONE (증거와 함께 종료)
```

각 사이클은 **작아야 한다.** "한 걸음(one step)"은 보통 *하나의 검증 가능한 변경*이다.
큰 작업은 여러 사이클로 쪼갠다.

---

## 2. 단계별 규칙

### [0] FRAME — 목표를 한 문장으로 고정
- 무엇이 끝났을 때 "완료"인지 **검증 가능한 완료 기준(Definition of Done)** 으로 적는다.
  - 나쁜 예: "버그 고치기"
  - 좋은 예: "X 입력 시 크래시 → 정상 표시. 회귀 테스트 1개 추가, 전체 테스트 green."
- 완료 기준이 모호하면 **여기서 멈추고** 사용자에게 1~3개 질문으로 좁힌다.

### [1] OBSERVE — 추측 금지, 관찰부터
- 고치기 전에 **관련 코드/파일/로그를 실제로 읽는다.** 기억이나 추측으로 진행하지 않는다.
- 넓게 찾아야 하면 검색 도구(Grep/Glob)나 탐색 에이전트로 fan-out 한다.
- 현재 상태의 **사실(facts)** 만 수집한다. 여기서 해법을 단정하지 않는다.

### [2] PLAN — 가장 작은 다음 한 걸음
- 지금 사이클에서 할 **단 하나의** 변경을 정한다. 여러 개가 떠오르면 목록으로 적고
  그중 **하나만** 고른다(나머지는 다음 사이클).
- 변경이 위험하거나(되돌리기 어렵거나 외부에 영향) 방향이 갈리면 실행 전에 사용자에게 확인.

### [3] ACT — 최소 변경
- 계획한 한 걸음만 실행한다. **scope creep 금지** — "겸사겸사" 다른 것 건드리지 않는다.
- 주변 코드의 스타일·관례·네이밍을 그대로 따른다.

### [4] CHECK — 검증 (이 루프의 심장)
- **도메인별 검증 명령을 반드시 실행한다.** (빌드/테스트/린트/실행/스크린샷 등)
  - 이 자리는 스킬마다 다르다. 참조하는 스킬이 채워 넣는다. (예: MFC면 빌드 + CppUnitTest)
- 검증 **출력을 실제로 본다.** "통과했을 것"이라고 가정하지 않는다.
- 결과를 정직하게 기록: 통과 / 실패(에러 원문) / 건너뜀(이유).

### [5] REFLECT — 배움을 다음 걸음에 반영
- **성공**이면: 무엇이 효과 있었는지 한 줄. 다음 걸음으로.
- **실패**면: 에러를 진단한다. **같은 변경을 그대로 재시도하지 않는다** — 가설을 바꾼다.
  - 같은 실패가 2회 반복되면 접근 자체를 의심하고 [1] OBSERVE로 더 깊이 돌아간다.
  - 3회 막히면 멈추고 진단·막힌 지점을 사용자에게 보고한다(무한 루프 금지).

### [6] DONE — 증거와 함께 종료
- 완료 기준(0번)을 **모두** 충족했고, 마지막 CHECK가 **green**일 때만 "완료"라고 말한다.
- 종료 시 한 일과 **검증 증거**(테스트 결과/빌드 로그 요약)를 함께 보고한다.

---

## 3. 진행 상황 추적 (status checklist)

사이클이 3개 이상이면 짧은 체크리스트를 유지하고 매 사이클마다 갱신한다.

```
- [x] (cycle 1) 입력 파싱 버그 재현 + 실패 테스트 추가
- [x] (cycle 2) NULL 가드 추가 → 테스트 green
- [ ] (cycle 3) 회귀 케이스 추가
- [ ] (cycle 4) 전체 스위트 재실행 + 정리
```

---

## 4. 안전장치 (가드레일)

- **무한 루프 금지**: 같은 단계 3회 연속 실패 → 멈추고 보고.
- **검증 없는 완료 금지**: CHECK를 건너뛴 채 "완료" 선언 금지.
- **되돌리기 어려운 행동**: 삭제/덮어쓰기/외부 전송/푸시 전엔 확인. 내가 만들지 않은 것을
  지우거나 덮어쓰기 전엔 먼저 내용을 확인하고, 설명과 모순되면 진행 대신 알린다.
- **정직한 보고**: 실패는 출력과 함께 실패라고, 건너뛴 건 건너뛰었다고 말한다.

## 5. 다른 스킬에서 쓰는 법 (계약, contract)

이 루프를 가져다 쓰는 스킬은 아래 "구멍"만 채우면 된다.

| 구멍 (hook)        | 채워 넣을 것                                  |
| ------------------ | --------------------------------------------- |
| `DoD`              | 도메인별 "완료" 정의 방식                       |
| `OBSERVE 대상`     | 어떤 파일/로그/도구로 관찰하는가               |
| `CHECK 명령`       | 빌드/테스트/실행 등 **검증 명령** (가장 중요)   |
| `REFLECT 기록처`   | 배움을 어디에 남기는가(없으면 대화 내)         |

예시(MFC PDCA 스킬에서):
```
이 작업은 @.claude/skills/loop/SKILL.md 의 6단계 루프를 따른다.
- CHECK 명령 = @.claude/skills/mfc-pdca/loop.md 의 "빌드+테스트" 절차
- 사이클 단위 = "실패 테스트 1개 → 최소 구현 → green" (TDD)
```
